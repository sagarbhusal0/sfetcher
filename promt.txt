# MASTER PROMPT: Build a Complete Free Video DownloadHelper Alternative

You are an autonomous senior software engineer specializing in Chromium extensions, TypeScript, browser networking, HLS/DASH streaming, and media processing. Your task is to **build a complete, working, free alternative to Video DownloadHelper**, primarily for Brave Browser on Linux.

Do not merely explain how to build it. Do not stop after creating a plan, generating boilerplate, or implementing a visual mockup. Inspect the repository, implement the software, run the available checks, fix errors, and leave the project in a working state.

If the repository already contains code, inspect it and preserve useful existing work. If it is empty, initialize the project yourself. Make reasonable technical decisions without repeatedly asking me for approval.

## 1. Product Requirements

Build a browser extension that detects downloadable media on the current webpage and lets the user inspect, select, and download supported media formats.

The extension must be:

- Completely free to operate.
- Local-first, without a required backend.
- Primarily compatible with Brave on Linux.
- Built with TypeScript, React, WXT, and Tailwind CSS.
- Based on Chromium Manifest V3.
- Designed to support HLS and MPEG-DASH VOD streams in addition to ordinary direct media URLs.
- Free from mandatory subscriptions, accounts, advertisements, analytics, telemetry, and paid APIs.
- Maintainable, documented, secure, and tested.

Do not copy proprietary source code, branding, logos, or assets from Video DownloadHelper. Create an original product identity and interface.

Use a temporary project name such as **OpenMedia Downloader** unless the repository already has a suitable name.

Use the following stack:

Avoid unnecessary dependencies. Do not load executable JavaScript from remote servers. Bundle all required runtime code locally.

## 4. Media Detection Engine

Implement actual media detection using supported browser APIs and content scripts.

Detect and classify:

- MP4.
- WebM.
- MOV and other recognized media containers.
- MP3, AAC, M4A, OGG, WAV, and other supported audio formats.
- HLS `.m3u8` playlists.
- MPEG-DASH `.mpd` manifests.
- HTML5 video and audio elements.
- Media URLs observed in network requests.
- Direct media resources identified by response MIME type.
- Resources loaded dynamically after the page has initially loaded.

Use multiple signals to reduce false positives:

1. URL path and file extension.
2. HTTP response `Content-Type` when available.
3. Resource type and network request metadata.
4. HTML media element properties.
5. Manifest contents and known streaming patterns.

Do not classify every binary request as a media resource.

Support dynamically created media elements by observing relevant DOM changes. Deduplicate detections and update metadata when additional information becomes available.

Use supported Manifest V3 network observation capabilities. Do not rely on blocking web requests or deprecated Manifest V2 APIs. Handle the limitations of observing response bodies and headers explicitly.

Where network observation cannot reliably identify a resource, use content-script discovery or offer a clear explanation.

### Media metadata

Collect and display, when available:

- Media type.
- Container and codec.
- Resolution.
- Duration.
- Source hostname.
- Approximate bitrate.
- Approximate file size.
- Audio language and track information.
- Subtitle and caption tracks.
- Detection time.
- Download status.

Never fabricate unavailable metadata. Distinguish between known, estimated, and unavailable values.

### Blob URLs

Handle `blob:` URLs as special cases. Investigate whether the underlying media can be identified through supported page-level observations or accessible manifests.

Do not assume a blob URL is directly downloadable through the background worker. If it cannot be safely accessed, explain the limitation in the UI.

Do not inject code to bypass browser security boundaries.

## 5. Direct Media Downloads

Implement fully functional direct downloading for accessible media URLs.

Use the browser Downloads API for normal direct resources whenever possible.

Required functionality:

- Start and cancel downloads.
- Show download progress.
- Show completed, failed, interrupted, and cancelled states.
- Display the destination filename.
- Allow filename editing before downloading.
- Sanitize filenames and remove unsafe path components.
- Handle duplicate filenames.
- Configure the default download subfolder.
- Retry recoverable failures.
- Track active downloads.
- Provide clear error messages.
- Reconcile persisted metadata with actual browser download state after a service-worker restart.

Support configurable concurrency for downloads managed by the extension itself.

Use browser-native download management for direct files where possible instead of reimplementing HTTP downloading unnecessarily.

Do not claim resumability unless the browser or implemented transport genuinely supports it.

For URLs that require temporary request context, handle failures clearly. Do not extract, store, log, or transmit passwords, authorization tokens, or cookies. Do not silently reuse credentials from unrelated origins.

Do not promise that downloads will work on every website. Display actionable errors for expired URLs, unavailable permissions, authentication restrictions, HTTP failures, and unsupported resources.

## 6. HLS Implementation

Implement HLS parsing and processing for authorized media streams.

Support:

- Master playlists.
- Media playlists.
- Relative and absolute segment URLs.
- Resolution and bandwidth variants.
- Codec metadata.
- Audio groups and alternate audio tracks.
- Subtitle tracks where available.
- Initialization segments.
- Fragmented MP4 segments.
- MPEG-TS segments.
- Media sequence numbers.
- Discontinuities.
- End-of-list markers.
- VOD playlist detection.
- Progress reporting.
- Cancellation.
- Recoverable retries.

Parse the playlist correctly instead of relying on fragile string matching.

Resolve relative URLs against the playlist's actual URL. Validate URL schemes and reject unsafe destinations.

For VOD playlists, provide an end-to-end pipeline:

1. Fetch the manifest.
2. Parse variants and available tracks.
3. Let the user select a representation and available audio or subtitle tracks.
4. Resolve the selected media playlist.
5. Retrieve the initialization segment when needed.
6. Retrieve segments in the correct order.
7. Preserve the metadata necessary for valid output.
8. Remux or package the segments into a supported playable output.
9. Report progress and clean up temporary data.

Do not simply concatenate arbitrary MPEG-TS or fragmented MP4 segments and rename the resulting file to `.mp4`.

Use a compatible remuxing strategy and verify output with suitable tests.

Support live streams only if a practical and tested recording implementation is possible. Otherwise, explicitly mark live-stream recording as unsupported in the initial release.

Do not implement DRM circumvention, encrypted-stream key extraction, or access-control bypasses.

## 8. Media Processing and FFmpeg

Evaluate the selected implementation for:

- Browser compatibility.
- Supported input containers.
- Supported output containers.
- Audio/video stream mapping.
- Codec compatibility.
- Memory consumption.
- Large-file limitations.
- Worker support.
- Distribution size.
- License compatibility.

If FFmpeg WebAssembly is selected, bundle the required runtime files locally and verify the worker and asset-loading paths in the built extension.

Never download an executable, codec binary, or JavaScript runtime from an external server at execution time.

Use separate processing workers when supported to prevent expensive media operations from freezing the popup or manager.

Do not load entire large videos into JavaScript memory unnecessarily. Implement bounded concurrency, chunk processing where practical, and explicit storage or memory limits.

If a selected format cannot be remuxed without transcoding, do not silently attempt an unsupported operation. Explain the issue and either select another compatible output or report the limitation.

Prefer stream copying and remuxing over transcoding whenever possible to minimize CPU usage and preserve quality.

The initial release must have a clear list of supported input/output combinations.
